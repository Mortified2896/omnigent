# Permanent Control Room peer-deployer

This document captures the architecture, threat model, authentication
design, and operational contract for the root-owned peer-deployer that
permanently supervises O1 and O2 upgrades on this host.

## Topology

```
            accepted artifact (541c9a31…)
                       |
                       v
+----------------------------------------+
| control-room-peer-deployer (root)      |
|   /opt/control-room-peer-deployer      |
|   /var/lib/control-room-peer-deployer  |
|   /run/control-room-peer-deployer      |
+-----^----------------------^-----------+
      |                      |
      | status/preflight/    | status/preflight/
      | promote              | promote
      |                      |
   O1 (hermes)            O2 (hermes)
   cgroup:                cgroup:
   omnigent.service       omnigent-production.service
   omnigent-host.service  omnigent-production-host.service
```

O1 and O2 both run under the same Unix UID (`hermes`).  Unix UID alone
is therefore not a sufficient identity.  The peer-deployer binds caller
identity to the systemd unit cgroup of the connecting process — see
`auth` below.

## Authentication

The peer-deployer accepts connections on a local Unix-domain socket at
`/run/control-room-peer-deployer/control.sock`.  For every accepted
connection it reads Linux `SO_PEERCRED` and inspects `/proc/<pid>/cgroup`.

| Hard rule | Reason |
|-----------|--------|
| Caller UID must equal `hermes` (uid 1000). | The Omnigent services run under this user; an arbitrary uid cannot speak for either instance. |
| Caller's systemd unit must be in `CGROUP_UNITS`. | The two instances share UID.  Only the cgroup identifies which instance issued the request. |
| `caller == target` is REFUSED. | "An instance NEVER upgrades itself." |
| `(caller, target)` must be `{(O1,O2), (O2,O1)}`. | Hard topology. |

The peer-deployer never trusts caller-supplied `supervisor` or `target`
fields for identity.  It trusts only kernel-provided pid/uid and the
cgroup string.

## Protocol

The wire format is one line of JSON terminated by `\n`.  Maximum request
size is 64 KiB.  Keys per `op` are strictly allow-listed:

* `status`: `op`, optional `tx_id`
* `preflight`: `op`, `target` (O1/O2), `accepted_sha`
  (must equal `541c9a3180b81bfb2fc450b3ef5f8648691b359d`), optional
  `request_id`
* `promote`: same as `preflight`

There are no `exec`, `command`, `path`, or `service` keys.  Paths and
service units are derived from the canonical O1/O2 identity tables —
they are never caller-supplied.

## Transaction eligibility

`peer_deployer/eligibility.py` is the authoritative decision point.  It
classifies every historical transaction into one of:

* `TERMINAL` — phase is in `tx_committed | rolled_back | failure`.  Does
  not block.
* `ACTIVE_UNRESOLVED` — non-terminal phase, no overlay.  Blocks.
* `VALIDLY_RECONCILED` — non-terminal phase, a vetted overlay declares
  the transaction safely cleaned.  Does not block.
* `INCONSISTENT_RECONCILIATION` — overlay does not match the
  transaction or is not a trusted class.  Blocks.
* `CORRUPT` — unreadable or missing transaction.json.  Blocks.

Historical records are immutable.  Classification is read-only and
never mutates `transaction.json`.

## Artifact trust

The peer-deployer only accepts the pinned accepted artifact:

```
sha    = 541c9a3180b81bfb2fc450b3ef5f8648691b359d
version= 0.9.0.dev0
```

The hard-coded `accepted_sha` allow-list in `service.py` is the single
source of truth.  No caller-supplied path can convince the peer-deployer
to install arbitrary bytes.

## Service layout

* `/opt/control-room-peer-deployer/releases/<commit>/`
  * `deploy/scripts/peer_deployer/` (the canonical package)
  * `venv/` (root-owned, offline site-packages)
  * `deploy/systemd/control-room-peer-deployer.service`
* `/var/lib/control-room-peer-deployer/`
  * `transactions/` — root-owned transaction records
  * `evidence/` — per-transaction evidence/logs
  * `artifacts/` — root-owned immutable artifact store
  * `locks/deployment.lock` — `flock`-protected exclusive lock
* `/run/control-room-peer-deployer/control.sock` — Unix IPC

## Systemd hardening

See `deploy/systemd/control-room-peer-deployer.service`:

* `ProtectSystem=strict`, `ProtectHome=read-only`,
  `PrivateTmp=true`, `NoNewPrivileges=true`
* `RestrictAddressFamilies=AF_UNIX` (no network surface)
* `SystemCallFilter=@system-service` minus privileged/raw-io/mount
  families
* `ReadWritePaths` allow-listed to the deployment roots only
* `ReadOnlyPaths` allow-listed to the supervised O1/O2 roots

## Bootstrap supply chain

The bootstrap installer (`deploy/scripts/control_room_peer_deployer_bootstrap.py`)
refuses to install a payload whose SHA-256 hashes do not match
`bootstrap-manifest.json`.  The manifest is generated by
`build_bootstrap_manifest.py` from a specific source commit BEFORE
the bootstrap is handed to the operator.  Bootstrap does not
`git pull`, does not `curl | sh`, and does not resolve PyPI.

## O1/O2 restart policy

* The peer-deployer does not depend on either O1 or O2 service unit.
* Bootstrap does not restart O1 or O2.
* The O1/O2 systemd units do NOT need to be restarted to inject the
  peer-deployer credential because the bootstrap authenticates callers
  via the existing cgroup membership of the already-running
  `omnigent*.service` units.  No reload of O1/O2 is required.
