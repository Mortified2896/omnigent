# Custom-change migration matrix

Forensic audit of the production fork (`refs/heads/legacy/custom-pre-0.7`,
`a4f20cab`) against upstream Omnigent **v0.7.0** (`35519fb0`). Every row
identifies the custom commit(s) it covers, the affected files, the upstream
state, and a recommended destination on `rebuild/upstream-0.7`.

The matrix was generated by:

1. `git diff --stat v0.7.0 legacy/custom-pre-0.7` (1 639 files, 147 705 / 259 168).
2. `git log --no-merges --cherry-pick --right-only --format=%H v0.7.0...legacy/custom-pre-0.7`
   (119 non-merge commits).
3. `git log --first-parent 255a5f8f..legacy/custom-pre-0.7` (100 commits,
   custom fork-only).
4. Per-commit `git show --stat --binary` for every topic commit
   referenced in the spec.
5. Manual review of the custom `omnigent/updater/`, `omnigent/deploy/`,
   `omnigent/agent_selector.py`, `omnigent/opencode_provenance_proxy.py`,
   `omnigent/runner/opencode_*.py`, `omnigent/runtime/harnesses/watchdog.py`,
   `omnigent/server/routing_agent.py`, `omnigent/server/smart_routing.py`,
   `omnigent/telemetry/*`, `omnigent/db/migrations/versions/z[a-g]*.py`, and
   `scripts/{promote_release,rollback_release,write-dropin,_deployed_sha,deploy_status,cleanup_releases,install_omnigent_updater,omnigent_updater,promote_main_deploy,install_eval_*_unit}.sh`.
6. Upstream search via `gh` for related issues / PRs (`omnigent-ai/omnigent`).
7. Spot-checks against the live `omnigent-ai/omnigent` tree for each
   candidate "already solved upstream" claim.

Categories:

1. Already solved upstream v0.7.0 — must not be re-ported.
2. Still required and should be ported (core or control-room layer).
3. Deployment-specific — must move outside `omnigent/` core.
4. Database-specific — only needed if the existing production DB is
   migrated; not required for a fresh 0.7 install.
5. Obsolete / harmful — do not port; some exist as obsolete deliberate
   broken-migration test artifacts.
6. Unclear / requires reproduction testing against a clean 0.7 install.
7. Suitable for an upstream contribution as a small, isolated patch.

## 3. Deployment-specific — move outside `omnigent/` core

The full external updater stack is in the fork. The intent is sound, but
the `omnigent/updater/` package, the `omnigent/deploy/ops/` and
`omnigent/deploy/supervisor/` packages, the `deploy/systemd/omnigent-updater.*`
files, and the twelve `scripts/install_*.sh / promote_*.sh / rollback_*.sh /
write-dropin.sh / deploy_status.sh / cleanup_releases.sh / omnigent_updater.sh
/ promote_main_deploy.sh` helpers are all single-tenant, hermes-targeted,
and require immutable release dirs under
`/home/hermes/workspace/deployments/omnigent/`. None of this is appropriate
in upstream Omnigent. The Phase 4 plan moves all of it into the Control
Room's `deploy/` subdirectory and ports the updater **contract** to
upstream only via the narrowest possible hooks (e.g. the identity-scoped
`HostRegistry.deregister`, the liveness-aware watchdog).
